Guided install

Choose how Keel should live.

Use it on one computer, keep it running at home, or put it on a server. These routes use the same application and can move the same workspace between them.

Before you start

Decide whether Keel should be available only on this machine, privately on your own devices, or publicly on the internet. Local and Tailscale installs have fewer moving parts. A public server needs deliberate access control and HTTPS.

GoalBest routeWhat you manage
Try Keel on one computerDesktop packageUpdates and backups
Use it across your own devicesHome server + TailscaleThe server, Tailscale, backups
Use a NAS or container hostDocker ComposeVolume, HTTPS, updates, backups
Reach it from anywhere without TailscaleVPS + reverse proxyDomain, server, HTTPS, access, backups
Account ownership: registration starts open. Server, source, and Docker installs ask you to register, then open Claim this server in Welcome or Settings. Generate the one-use command and run it on the server within five minutes. macOS and Linux require a fresh sudo prompt; Windows requires Administrator PowerShell. The browser never asks for that password. The loopback-only desktop app assigns controls to its first local workspace owner automatically and shows no terminal claim step. Claiming does not close registration; the owner chooses when to close it in Settings.

Windows

Desktop setup

  1. Download Keel Setup 1.2.2.exe from the official release.
  2. If SmartScreen appears, check that the file name and GitHub origin are correct, select More info, then Run anyway. Stop if the source is not the official release.
  3. Complete setup and open Keel. The first start can take longer while the local database is created.
  4. Register the owner account, finish the welcome tour, then create and download a test backup from Settings.

Always-on PowerShell service

irm https://raw.githubusercontent.com/AES256Afro/Keel/main/install.ps1 | iex

For a custom location or port, download the script and run .\install.ps1 -Dir C:\Keel -Port 3000 -Service. Open Task Scheduler and confirm the Keel task is running.

macOS or Linux service

  1. Open Terminal on the machine that will run Keel.
  2. Run the guided installer. Add --service so it starts automatically.
  3. Read the final summary. It prints the install folder, data path, service name, and URL.
  4. Open http://localhost:3000 and register the account you want to operate the server. Registration is open by default.
  5. In Welcome or Settings, open Claim this server and generate a one-use command bound to the signed-in account.
  6. Run that exact command in the install folder within five minutes. Enter the operating-system password only at the fresh sudo prompt.
  7. Refresh Settings, choose when to turn off Allow new registrations, and download a test backup.
  8. Optional: add Google sign-in, Drive, OneDrive, or OneNote from Settings -> Integrations. Secrets are write-only, changes apply immediately, and the page gives you the exact callback URLs.
curl -fsSL https://raw.githubusercontent.com/AES256Afro/Keel/main/install.sh | bash -s -- --service

Useful options: --dir ~/keel, --port 8080, and --yes. The older --owner option is accepted for compatibility but grants no authority. Local registration stays open until the claimed owner changes it. Re-running the installer updates the application and preserves existing access settings.

Docker Compose

  1. Install Docker Engine or Docker Desktop and confirm docker compose version reports 2.30 or newer.
  2. Clone Keel and copy .env.example to .env. Registration starts open; use the signed-in claim flow instead of an email-based owner selector.
  3. Run docker compose up -d --build.
  4. Run docker compose ps. Wait for the service to report healthy, then open http://127.0.0.1:3000. The base stack does not publish port 3000 to the LAN.
  5. Register, generate a one-use token from Claim this server, then run docker compose exec --user root -e KEEL_CONTAINER_CLAIM=1 keel npm run claim -- 'one-use-token'. On Linux, first run sudo -k, then prefix the Docker command with sudo. With Docker Desktop, use it without sudo from a terminal with daemon access.
  6. Refresh Settings and decide whether to close registration. Claiming does not change that policy.
  7. Create a backup and confirm you can find it outside the container.
Do not scale SQLite horizontally. Keep one Keel application replica with the SQLite volume. If a managed platform has no durable disk, build the PostgreSQL image and attach a managed PostgreSQL database.

Compose reads application env files in raw mode, so dollar signs in passwords and tokens remain literal. Production Caddy receives only the hostnames in .env.caddy; it never receives the app secrets in .env.prod.

After the server is claimed, Google and Microsoft OAuth credentials can be managed from Settings -> Integrations. Saved secrets are write-only and encrypted under a host key kept outside the database. The owner can also edit the public-site name, tagline, and Notes URL, save a write-only scheduled-backup passphrase, and review a secret-free effective-configuration summary in Settings. Environment values remain available as locked deployment overrides. Database URLs, network binding, proxy trust, cookie scope, WebAuthn origins, filesystem paths, and service supervision stay on the host.

Update with git pull --ff-only && docker compose up -d --build. Read the release notes first and keep a recent backup.

Private home server

This is the recommended multi-device route when only your own devices need access.

  1. Install Keel on the server with the shell installer or Docker.
  2. Install Tailscale on the server and your client devices. Sign them into the same tailnet.
  3. On the server, run tailscale serve --bg 3000.
  4. Set KEEL_WEBAUTHN_RP_ID to the server's *.ts.net hostname and KEEL_WEBAUTHN_ORIGIN to the complete HTTPS URL.
  5. Restart Keel and confirm the HTTPS address works from a second tailnet device.

This route does not create public DNS and does not require opening port 3000 on the router.

Public VPS

Use a small Debian or Ubuntu server with Docker, a domain, and a reverse proxy such as Caddy. Point DNS to the server before requesting a certificate.

  1. Set KEEL_ALLOWED_EMAILS to the intended account. Do not use an owner-email override to bootstrap a new deployment.
  2. Stop the public reverse proxy or firewall ports 80 and 443. Keeping the URL unshared is not access control.
  3. Bootstrap the administrator with docker-compose.bootstrap.yml and ssh -L 3000:127.0.0.1:3000 <ssh-user>@<server-ip>, a private network, or verified Google sign-in. An email allowlist alone does not prove mailbox ownership.
  4. For a local SQLite host, generate a one-use command and confirm it from the server terminal. For managed PostgreSQL, generate a 32-byte KEEL_OWNER_BOOTSTRAP_TOKEN, paste it into Keel's write-only hosted claim field, then remove it from the platform secret store and restart.
  5. Set KEEL_DISABLE_SIGNUP=1, which unconditionally blocks every new account, before exposing the server.
  6. Set KEEL_PUBLIC_URL, WebAuthn origin, and relying-party ID to the final HTTPS hostname.
  7. Put Keel behind HTTPS. Set KEEL_TRUST_PROXY=1 only when your reverse proxy overwrites or appends the forwarding headers.
  8. Recreate Keel from the production Compose file alone to remove the temporary port, start the proxy, and confirm /api/health reports OK over the public hostname.
  9. Configure an off-machine backup destination and test a restore before trusting the deployment.

Cloudflare can provide DNS, proxying, a Tunnel, and R2 backup storage. Keel itself is a Node server and does not run on Cloudflare Workers today.

Troubleshooting

The page does not open

Confirm Keel is running, then try http://127.0.0.1:3000. For Docker, inspect docker compose ps and docker compose logs --tail=100. For a service install, use the exact status and log commands printed by the installer.

Another program uses port 3000

Choose another port during install, for example --port 8080, or set the deployment's PORT value. Then open that port in the browser.

The administrator email cannot register after a 1.2.1 CLI install

Re-run the current guided installer. Keel 1.2.2 recognizes the exact affected empty local configuration, removes the accidental hard signup stop, and restarts a known managed service. If you started Keel manually, stop that process and start it again. Register normally, then generate the one-use claim command in Welcome or Settings.

Settings says this server is unclaimed

Open Claim this server, generate a command, and run it on the Keel machine within five minutes. The token is bound to the signed-in account, can be used once, and is replaced when you generate another. On macOS or Linux, enter the operating-system password only into the fresh sudo prompt in Terminal. On Windows, use an Administrator PowerShell. Never enter that password into the browser. Refresh Settings after the command succeeds.

Security keys do not register

WebAuthn needs HTTPS or localhost. Confirm the browser URL exactly matches KEEL_WEBAUTHN_ORIGIN and that the relying-party ID is only the hostname.

A public server allows unexpected registration

Stop the service, set KEEL_ALLOWED_EMAILS and KEEL_DISABLE_SIGNUP=1, restart, and review the audit log. Do this before sharing the URL.

You are unsure where data lives

Run keel paths for a CLI install. In Docker, inspect the named volume. Do not guess, and do not delete an install until a backup has been restored successfully elsewhere.

For a reproducible software bug, open an issue. For a vulnerability, use the private security report.
